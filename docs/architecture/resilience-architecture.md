# Resilience Architecture

## Current failure handling: minimal

No resilience library is present in `pom.xml` — no Resilience4j, no Spring Retry, no Spring Cloud Circuit Breaker. No `@Retryable`, no `@CircuitBreaker`, no explicit timeout configuration on the outbound HTTP/SDK clients that were read (`EmailService`/`spring-boot-starter-mail`, `TwilioOTPService`/Twilio SDK, `S3Service`/AWS SDK, `PdfService`/iText — all synchronous, none observed to be wrapped in retry/circuit-breaker logic during this pass). This matches the honest baseline stated in `event-architecture.md`: nothing async or fault-tolerant exists today beyond whatever the underlying libraries do by default.

Concretely, in the monolith today:
- **Single point of failure by design, not accident**: since everything is one process and one database, a failure in Product Catalog code (e.g. a bug in `ExcelProductImportServiceImpl`'s bulk import) shares the same JVM, thread pool, and DB connection pool as Order placement — an unbounded/long-running import can starve Order's ability to serve requests. There is no bulkhead between domains.
- **No visible global exception handling**: no `@ControllerAdvice`/`@RestControllerAdvice` was found applied broadly across the 59 controllers during this pass — error responses likely default to Spring Boot's built-in `/error` handling (partially reconfigured via `server.error.include-*` in `application-dev.yml`), meaning error shape/consistency across domains is not guaranteed to be uniform.
- **No idempotency keys observed** on write endpoints (order placement, payment, approval) — a retried request (client timeout + retry, or a double-click) has no visible dedupe mechanism in the service methods read (e.g. `OrderPlacementServiceImpl` was not observed checking for an existing order before creating a new one from the same request).
- **Transactional boundaries are implicit**: multi-repository writes (e.g. `OrderPlacementServiceImpl` writing `Order`+`OrderItem`+`SellerOrder`+`Payment`, or `SellerApprovalServiceImpl` writing `Seller` + its children while reading `TempSeller`) rely on Spring's default `@Transactional` propagation — this works today because it's one database, but is exactly the safety net that disappears once services and databases split (see below).
- **External-provider failures are synchronous and unmitigated**: if Twilio, the mail SMTP host, or S3 is slow/down, the calling request (seller/buyer OTP send, approval-notification email, document upload) fails or hangs with the caller getting whatever the SDK's default timeout is — no fallback, no circuit breaker, no fast-fail with graceful degradation was found.

## What would be needed post-split (proposed, not implemented anywhere today)

| Pattern | Why it's needed once services are separate |
|---|---|
| **Circuit breakers** (e.g. Resilience4j) on every synchronous cross-service call identified in `api-dependency-analysis.md`/`database-ownership.md` — Order→Buyer, Order→Product (pricing/stock), Product→Seller (seller_id validation), Seller/Buyer→Master-Reference | Prevents one degraded downstream service (e.g. Product Catalog under bulk-import load) from cascading failure into Order placement or Seller registration. |
| **Timeouts on every outbound call**, explicit and short, replacing today's implicit SDK defaults | A hung call to a downstream service must not hold a thread indefinitely, especially once these calls cross a network boundary instead of being in-process method calls. |
| **Retries with backoff** for idempotent reads (Master/Reference lookups, product/seller detail fetch) — NOT for the order-placement write path without an idempotency key first | Naive retries on non-idempotent writes (e.g. re-submitting an order) would create duplicate orders/payments if not paired with idempotency keys. |
| **Saga + compensation** for order placement (see `event-architecture.md` #1) — replacing today's single local `@Transactional` spanning Buyer+Product+Order tables | Once Buyer, Product, and Order are separate databases, there is no ACID transaction across them; a stock-reservation failure after an order row is created needs an explicit compensating action (cancel order), not an automatic rollback. |
| **Idempotency keys** on Order placement, Payment, and Seller/Buyer approval endpoints | Required once retries (client-side or gateway-side) become likely across network boundaries; currently masked by the monolith's low-latency in-process calls. |
| **Bulkheads** — separate thread pools / connection pools per downstream dependency (already naturally achieved once services are physically separate, but should also be applied *within* Product Catalog between the bulk-import path and the interactive catalog-browse path) | Prevents a large Excel import from starving interactive product-browsing requests, whether or not the service split happens. |
| **Dead-letter handling** for the async events proposed in `event-architecture.md` (stock-restore-on-cancel, approval notifications) | An event that repeatedly fails to process (e.g. malformed payload, downstream service down past retry budget) needs a DLQ and alerting rather than being silently dropped or retried forever. |
| **Health checks / readiness probes** per service, feeding a load balancer or orchestrator | Not present today because there's only one deployable; becomes necessary the moment there are 5 independently-deployed services with independent failure modes. |

## Recommendations independent of any microservice split

1. Add a global `@RestControllerAdvice` for consistent error response shape across all 59 controllers — low effort, immediate consistency win, and a prerequisite for building client-side retry logic sensibly later.
2. Wrap `EmailService`, `TwilioOTPService`, `S3Service`, `PdfService` calls with explicit timeouts and at least basic retry-with-backoff (Spring Retry is a small dependency to add) before any service extraction — this hardens the monolith regardless of the migration timeline.
3. Add idempotency-key support to `OrderPlacementServiceImpl` and the approval endpoints now, while it's a single-database local change, rather than retrofitting it under the added pressure of a distributed-transaction rewrite later.
4. Treat the Order-placement saga design (see `event-architecture.md`) as a **prerequisite deliverable**, not an afterthought, before Product Catalog or Buyer & Onboarding are extracted as separate deployables — extracting them without first designing the compensation flow for stock/payment failure risks silent data inconsistency (e.g. an order recorded with no stock actually reserved).
